# 00. 워크북 사용법

## 목표

3회차 워크북의 진행 방식을 이해합니다.

## 왜 하는가

3회차는 1·2회차보다 참가자 화면 차이가 커집니다.
누군가는 Home만 있고, 누군가는 Projects 카드가 있고, 누군가는 Pages 배포가 아직 실패 상태일 수 있습니다.

그래도 공통으로 할 수 있는 일은 같습니다.

```text
화면을 본다
→ 고칠 영역을 고른다
→ 문제를 말로 쓴다
→ Codex에게 계획을 받는다
→ 작은 수정만 한다
→ 브라우저와 모바일에서 확인한다
```

## 오늘의 핵심 도구

| 도구 | 오늘 쓰는 의미 |
|---|---|
| Codex in-app browser | 로컬 홈페이지 화면을 Codex와 함께 보는 브라우저 |
| Browser comments | 화면의 특정 요소나 영역에 다는 주석 |
| Screenshot | 현재 상태를 보여주는 증거 |
| Viewport | 브라우저 화면 크기. 예: 390x844 |
| Inspect / page inspection | 선택한 요소의 CSS 원인을 확인하는 방법 |
| `npm run build` | 배포 가능한 상태인지 확인하는 명령 |

## 3회차 기본 규칙

### 1. "예쁘게"라고만 말하지 않습니다

```text
나쁜 요청:
좀 더 예쁘게 해줘.

좋은 요청:
Home 첫 화면의 제목과 소개 문장 사이 간격이 너무 넓어 보여.
모바일 390px에서는 제목이 4줄로 깨져.
전체 톤은 유지하고 제목 크기와 섹션 간격을 줄이는 계획을 먼저 제안해줘.
```

### 2. 수정 전 계획을 받습니다

```text
아직 파일을 수정하지 말고, 먼저 원인 후보와 최소 수정 계획을 설명해줘.
내가 승인하면 진행해줘.
```

### 3. 한 번에 하나의 영역만 고칩니다

오늘은 디자인 전체 리뉴얼이 아닙니다.
Home hero, Navigation, Projects 카드, Posts 목록 중 하나를 고르고 작은 수정부터 합니다.

### 4. 모바일 확인은 선택이 아닙니다

데스크톱에서 좋아 보여도 모바일에서 깨질 수 있습니다.
최소 390px 폭에서는 확인합니다.

## 막혔을 때 기본 질문 템플릿

```text
나는 3회차 워크북의 [단계 이름] 단계에 있어.
현재 프로젝트는 Astro 개인 홈페이지이고 Codex를 쓰고 있어.

현재 상태:
- 열린 URL:
- 고치고 싶은 영역:
- 화면 크기:
- 문제:
- 원하는 방향:

제약:
- 새 라이브러리는 추가하지 마.
- 관련 없는 파일은 수정하지 마.
- 기존 데이터 구조는 유지해.
- 아직 수정하지 말고 원인 후보와 다음 한 단계만 제안해줘.
```
