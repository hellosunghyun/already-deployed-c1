# 02. 디자인 baseline 기록하기

## 목표

수정하기 전 현재 화면 상태를 기록합니다.

## 왜 하는가

디자인 수정은 before / after 비교가 있어야 의미가 있습니다.
수정 전 화면을 기록하지 않으면 어떤 변화가 좋아졌는지, 무엇이 나빠졌는지 판단하기 어렵습니다.

## baseline에 기록할 것

```text
URL:
Viewport:
화면에서 먼저 보이는 것:
읽기 어려운 부분:
클릭하기 어려운 부분:
모바일에서 의심되는 부분:
유지하고 싶은 부분:
```

## Codex에게 보낼 프롬프트

```text
3회차 디자인 수정을 시작하기 전에 현재 화면 baseline을 기록하고 싶어.

Codex Browser로 아래 페이지를 열어줘.

- /
- /about
- /projects
- /posts

각 페이지를 보면서 아래 기준으로 관찰해줘.

1. 화면에서 가장 먼저 눈에 들어오는 요소
2. 제목과 설명의 위계가 분명한지
3. 여백이 너무 좁거나 넓은 곳
4. 링크나 버튼이 클릭 가능한 것처럼 보이는지
5. Projects 카드나 Posts 목록이 읽기 쉬운지
6. 모바일에서 깨질 가능성이 있는 곳
7. 유지하면 좋은 점

중요:
- 아직 수정하지 마.
- 디자인 취향으로 단정하지 말고, 관찰 가능한 문제만 말해줘.
- 문제를 P0 / P1 / P2로 나눠줘.
  - P0: 사용을 방해함
  - P1: 읽기 어렵거나 이동이 헷갈림
  - P2: 더 좋아질 수 있는 개선점
```

## 관찰 예시

```text
P1 / Home / desktop
Hero 제목과 소개 문장 사이 간격이 너무 넓어 첫 화면에서 다음 행동이 약해 보임.

P1 / Projects / 390px
카드 내부의 제목, 역할, 도구 태그가 모두 비슷한 시각 무게라 훑어보기 어려움.

P2 / Posts / desktop
날짜와 태그가 본문보다 강하게 보여 글 제목이 덜 눈에 들어옴.
```

## 체크박스

- [ ] Home baseline을 기록했다.
- [ ] About baseline을 기록했다.
- [ ] Projects baseline을 기록했다.
- [ ] Posts baseline을 기록했다.
- [ ] P0 / P1 / P2 중 최소 3개 문제를 적었다.
- [ ] 유지하고 싶은 부분을 최소 1개 적었다.

## Ready Gate

다음 단계로 넘어가기 전에 아래가 되어 있어야 합니다.

- 수정 전 화면 상태가 기록되어 있습니다.
- 고치고 싶은 문제를 최소 1개 골랐습니다.
- 유지하고 싶은 부분을 알고 있습니다.
